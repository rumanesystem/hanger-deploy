1. 왜 바꾸나

지금 구조의 근본 문제:
  • 발주서 222건이 hanger_data/orders 문서 1개의 value 필드에 단일 배열로 저장
  • 발주서 1건 수정 = 222건 통째로 덮어쓰기
  • 여러 사람 동시 작업 시 → 마지막 쓰기가 모든 것을 이김 → 데이터 사라짐
  • 핫픽스를 아무리 추가해도 구조 자체가 안 바뀌면 새로운 사고 패턴이 또 나옴

지금까지 패치 이력

날짜대응한계
5/19localStorage→서버 우선 전환 (1단계)구조 그대로
6/8발주서 3건 영구 손실 사고—
6/9008 발주서 사라짐—
6/11핫픽스 A, B' (서버 재조회 + merge)shipping.js 우회 경로 잔존
6/111단계 inflight 가드 + submitEditOrder 단일 write다중 기기 race 남음
6/11핫픽스 C (watchData/_mem 병합)구조 그대로
모든 패치가 같은 본질(단일 배열 통째 쓰기)을 우회하려는 시도. 구조 변경이 진짜 해결.

2. 새 구조

현재 (위험)

hanger_data/
  orders          ← 문서 1개 안에 발주서 222건 배열로 통째 저장
    value: [
      {id:1, orderNum:"20260601-001", ...},
      {id:2, orderNum:"20260601-002", ...},
      ... 222건
    ]

변경 후 (안전)

hanger_orders/                    ← 새 컬렉션
  20260611-001    ← 발주서 1건 = 문서 1개
  20260611-002
  20260611-003
  ...
  20260608-001    ← 옛 데이터도 그대로 이전
발주서 수정 = 그 문서 1개만 수정. 다른 발주서는 손도 안 댐. 동시 작업해도 충돌 자체가 불가능.

4. 안전 장치

4.1 즉시 차단 스위치 (런타임 플래그)

hanger_data/runtime_flags
{
  ordersDualWrite: true,       // 끄면 옛 경로만
  ordersReadFromNew: false,    // 켜면 새 경로 우선 읽기
  ordersBlockLegacyWrite: false // 켜면 옛 경로 쓰기 차단
}

사고 발생 즉시 Firestore Console에서 플래그만 바꿔도 영향 차단.
