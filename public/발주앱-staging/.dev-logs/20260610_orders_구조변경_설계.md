## 0. 배경 요약

- **사고**: 6월 8일 발주서 3건이 누군가의 로컬 캐시가 서버를 통째로 덮어쓰면서 사라짐. 복구는 완료.
- **근본 원인**: `hanger_data/orders` **단일 문서**의 `value` 필드에 발주서 222건이 **단일 배열**로 저장됨.
- `DB.set('orders', orders)` 한 번 호출 = `_FS.set('orders', toStore)` = 문서 통째 덮어쓰기.
- 두 PC가 동시에 set 하면 마지막 write가 모든 것을 이김. `_GUARD` 병합 로직이 있지만 **`_mem` 메모리 미러 vs Firestore 실값** 사이의 시차 때문에 stale 데이터가 그대로 새로 들어온 데이터 위로 덮을 수 있음.

- **목표**: `orders/{docId}` 컬렉션 구조 (발주서 1건 = 문서 1개) 로 전환해 "발주서 쓰기는 발주서 쓴 사람만의 단일 문서 쓰기"로 격리.

- `drawerItems`: 평균 3~8건, 최대 20건 추정

### B.3 222건 총 크기

- 평균 5KB × 222건 ≈ **1.1 MB** — Firestore 단일 문서 1MB 한계에 매우 근접. **이미 위험 수준**.
- 이게 사고 외에도 새 구조 전환이 시급한 두 번째 이유.

## 섹션 C. 새 컬렉션 스키마 제안

### C.1 컬렉션 이름 (제안)

**제안: `hanger_orders`**
- 이유: 기존 `hanger_data` 와 같은 prefix 유지로 보안 규칙·백업 함수 패턴 재사용 용이.
- 대안 ①: `orders` (최상위) — 규칙 추가 필요, 다른 앱 충돌 가능성. 비추천.
- 대안 ②: `hanger_data_orders` — 너무 김. 비추천.

### C.2 문서 ID 전략 (제안)

**제안: `orderNum` 그대로 문서 ID 사용 (예: `20260608-001`)**

장점:
- 자연키 — UI URL이나 검색에서 그대로 사용
- 같은 발주서를 두 번 만들 수 없음 (PK 자체가 중복 차단)
- 문서 직접 lookup 가능 (orderNum 알면 `.doc(orderNum).get()`)

단점:
- 발주번호 변경(거의 없음) 시 doc 이동 필요

대안: 자동 ID + `orderNum` 필드 인덱스.
- 장점: 발주번호 수정 자유로움.
- 단점: 자연키 활용 불가, 항상 `where('orderNum','==',...)` 쿼리 필요.

**개발자님 결정 필요** (섹션 G).

### C.3 인덱스 필요 항목

기본(자동): `__name__` (= orderNum)
복합 인덱스 후보:
- `status` + `orderDate desc` — 발주 목록 기본 정렬
- `createdBy` + `orderDate desc` — 본인 발주만 보기
- `warehouse` + `status` + `orderDate desc` — 창고별 출고 현황
- `status` + `shipDate` — 출고 일정 화면
- `deliveryTo` (단일) — 거래처별 검색

Firestore는 단일 필드 인덱스는 자동. 복합만 명시 필요 (`firestore.indexes.json`).

### C.4 statusHistory subcollection 분리?

**제안: 분리 안 함 (배열 유지)**.
- 한 발주서당 평균 3~7건 — 별도 subcollection 의 read 횟수·비용 증가 대비 이득 없음.
- 단일 문서 크기 한계도 한 건당 8KB 수준이라 여유 충분.
- 단, **drawerItems 가 50건 이상 들어가는 거대 발주서**가 향후 있으면 그때 subcollection 검토.

**개발자님 결정 필요** (섹션 G).

### C.5 새 스키마 요약

```
hanger_orders/{orderNum}
├── id: number              # 기존 호환
├── orderNum: string        # 문서 ID와 동일 (중복 저장하지만 호환성용)
├── status: string
├── deliveryTo, address, orderDate, shipDate, warehouse, note: ...
├── upperMaterials, rodItems, shelfItems, drawerItems: array
├── totalSupply, totalVat, totalAmount: number
├── stockDeducted: boolean
├── ecountSlipNos: array<string>
├── createdBy, createdAt, updatedAt: string
├── cancelReason, cancelledAt: string?
├── statusHistory: array<object>     # 분리 안 함
├── _schemaVersion: 2                # 새 구조 마커 (필수 — 마이그레이션·롤백 판단)
└── _migratedFrom: 'hanger_data/orders'?  # 마이그된 건 표시 (선택)
```

기존 `hanger_data/orders` 문서는 **읽기 전용 유물(legacy)** 로 남김.

## 섹션 D. 마이그레이션 전략

### D.2 듀얼 라이트 (2단계) 설계

`DB.set('orders', orders)` 호출은 그대로 두되, `_FS.set` 내부에서:
1. 기존 경로 (`hanger_data/orders`): 배열 통째 — **사고 위험은 동일하므로 단계 5까지 유지하되 빨리 진행**
2. 새 경로 (`hanger_orders/{orderNum}`): **변경된 발주서만** 단건 set

문제: `DB.set('orders', orders)` 는 "전체 배열"을 받음. 무엇이 바뀐 건지 알 수 없음.

**해법 1**: `DB.set` 호출부를 점진적으로 `DB.upsertOrder(orderDoc)` (단건 API) 로 교체. 9곳 (W) 모두.
- 작업량 큼 (각 호출자가 "어떤 발주서를 바꿨는지" 명확해야 함)
- 다행히 거의 모든 호출자가 `orders[idx]` 단건 변경 → DB.set 전체 패턴이라 변환 가능.

**해법 2**: `DB.set('orders', ...)` 내부에서 이전 배열과 diff 떠서 변경된 발주서만 새 컬렉션에 set.
- 단순. 호출부 변경 0.
- 단점: diff 비용. 동시 PC 환경에선 "이전 배열" 자체가 stale 일 수 있어 안정성 의문.

**제안: 해법 1**. 다만 단계 2 시작 전 호출부 정리 PR 1개 먼저 (영향 큰 9곳 → 단건 API 호출로 변환). 그 다음 듀얼 라이트 활성.

### D.3 백필 스크립트 (3단계)

위치: `functions/migrate-orders-to-collection.js` (일회성).

동작:
```
1. hanger_data/orders 의 value 배열 읽기 (222건)
2. 각 건에 대해:
   - docId = order.orderNum (없으면 'NOID_' + order.id)
   - hanger_orders/{docId} 에 set (merge 옵션은 안 씀 — 깨끗하게 새로 씀)
   - _schemaVersion: 2, _migratedFrom: 'hanger_data/orders', _migratedAt: now 추가
3. 222건 모두 성공 시에만 종료. 1건이라도 실패 시 전체 롤백 (이미 만든 문서 삭제).
4. 검증: count = 222 + 배열 길이 동일 확인
```

배치: 500건 단위로 batch (Firestore batch 제한 500). 222건은 1배치.

### D.4 검증 방법

- 백필 직후: 두 곳 count 동일 + 각 orderNum 의 totalAmount 합계 동일
- 듀얼 라이트 기간: 매일 한 번 KST 02:00 비교 함수 (Cloud Function) — 차집합 0 확인
- 1주 동안 차집합 0 유지 시 단계 4 (읽기 전환) 진행

### D.5 데이터 변환

기본은 그대로 복사. 단:
- `id` 가 누락된 매우 오래된 데이터 있으면 자동 부여
- `statusHistory` 가 없는 건 빈 배열로
- `siteName`/`customerName` 같은 하위 호환 필드는 그대로 두기 (단계 5 이후 별도 정리)

## 섹션 F. 회귀 위험 + 롤백 계획

### F.1 가장 큰 위험 1: 듀얼 라이트 중 일관성 깨짐

시나리오: PC-A가 발주서 #100 의 status 를 '발주확정' 으로 변경 → 새 경로엔 반영, 옛 배열엔 (네트워크 끊김으로) 반영 실패. 그 사이 PC-B가 옛 배열을 읽고 다른 발주서 #101 수정 → 옛 배열을 set → #100 의 옛 status('발주대기')가 다시 쓰여짐.

**대응**: 듀얼 라이트는 **항상 새 경로 먼저, 옛 경로는 사후 mirror 로**. 옛 경로 실패는 경고만 기록 + 일일 비교 Cloud Function이 잡아 보정.

### F.2 가장 큰 위험 2: orderNum 충돌·미발급

`generateOrderNum()` 의 시드 계산이 `hanger_data/orders` 의 배열을 스캔. 새 컬렉션으로 전환하면 시드 소스도 바꿔야 함.
**대응**: 시드 소스를 `hanger_orders` collection 의 `where('orderNum','>=','YYYYMMDD').orderBy('orderNum','desc').limit(1)` 쿼리로 변경. 또는 카운터 문서(`orderseq_*`) 만으로 충분하게 단계 5에서 시드 로직 자체 제거.

### F.3 위험 3: stockDeducted 플래그 양쪽 불일치

가장 사고가 잘 나는 필드. 듀얼 라이트 중 한쪽만 반영되면 **재고가 이중 차감되거나 누락**.
**대응**: 듀얼 라이트 트랜잭션화 (가능하면 `batch.set + batch.set` 한 묶음). 양쪽 모두 성공해야 commit. 부분 실패 시 옛 경로는 best-effort 로 보정.

### F.4 위험 4: shipping.js #22 의 DB 레이어 우회

이 한 줄이 `_GUARD` 병합 로직을 완전히 우회. 출고 확정 시 stale 한 orders 배열로 서버를 덮어쓸 수 있음. **사고 6/8의 가장 유력한 단일 원인 후보 중 하나**.
**대응**: 단계 2 시작과 동시에 #22를 `_FS.upsertOrder` 단건 set 으로 즉시 변경. 다른 변경 없이 이 한 줄만 먼저 고쳐도 사고 재발 가능성 크게 감소.

### F.5 단계별 롤백 안전점

- 단계 2 후: feature flag 끄면 듀얼 라이트 OFF, 옛 단일 문서 그대로 운영
- 단계 3 후: 새 컬렉션 삭제 (옛 단일 문서는 그대로 살아있음)
- 단계 4 후: 읽기 경로만 옛 경로로 복귀 (코드 1줄 flag)
- 단계 5 후: ⚠️ 신규 발주서가 새 컬렉션에만 있음. 롤백하려면 새 → 옛 으로 역백필 필요

### F.6 즉시 차단 스위치

`hanger_data/runtime_flags` 문서 안에:
```
{
  ordersDualWrite: true,    # 끄면 옛 경로만
  ordersReadFromNew: false, # 켜면 새 경로 우선
  ordersBlockLegacyWrite: false  # 켜면 옛 경로 set 차단 (단계 5)
}
```
앱 부팅 시 1회 fetch 해서 _runtime 에 들고 있음. 사고 발생 즉시 콘솔에서 flag 변경 → 영향 차단.
