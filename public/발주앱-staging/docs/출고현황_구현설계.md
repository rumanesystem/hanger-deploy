## 0. 핵심 실측 결과

### ✅ 품목 합산 가능 — 자유 텍스트 아님, 코드/드롭다운 기반
| 구역 | 합산 키 | 근거 |
|---|---|---|
| 상부자재 | `name` (UPPER_FIXED 드롭다운 고정값) | 오타 없음 |
| 옷봉 | `rodItems[].size` (mm 정수 문자열) | 입력 시 정수 강제 |

- 출고창고 `o.warehouse` (`"시흥"`|`"평택"`)
- 상태 `o.status` — 대상: `'발주확정'` 또는 `'출고준비'`

## 2. shipping.js 함수 구성

```
renderShippingView()              진입점, #content 렌더
getShippingOrders(wh, dateFilter) 창고·날짜·상태 필터
getDateRange(filter)              오늘/내일/이번주 날짜범위
aggregateShippingItems(orders)    ★구역별 품목 합산 (Map 4개)
renderAggregateTable(agg, orders) 합산 테이블 HTML
renderDetailRows(...)             아코디언 상세(납품처별 + 출고완료 버튼)
handleShipComplete(orderId)       changeOrderStatus(,'출고완료') 후 재렌더
onShippingWarehouseChange / onShippingDateChange  필터 핸들러
```

데이터 흐름: `await window._FS.get('orders')`(서버 직접) → 수신 성공 시에만 → 필터 → 합산 → 테이블 렌더 → #content
서버 미수신/실패 시 → 렌더 중단 + "새로고침" 안내 (로컬 폴백 절대 금지, 7-A 참조)
→ renderShippingView()는 `async`. getShippingOrders()는 인자로 서버에서 받은 orders 배열을 받음(자체 조회 금지).

## 7-A. 🔴🔴 데이터 접근 규칙 (절대) — 서버만 읽는다. 로컬 폴백 일절 금지

> 개발자 강조(2026-06-01): **서버 미수신이어도 로컬을 읽지 마라. 과거에 서버 안 보고 로컬만 봐서 정보가 크게 꼬였다.**

### 왜 `getOrders()`를 쓰면 안 되나 (꼬임의 근원)
`getOrders()` → `DB.get('orders')` → `window._mem` 을 읽는데, db.js의 `syncFromServer()`는
**서버 수신 실패 시 `_loadLocalFallback()`로 localStorage(`sh_*`)를 `_mem`에 적재**한다.
→ 결국 `getOrders()`는 서버 미수신 상황에서 **로컬 데이터를 서버 데이터인 척 반환**한다. 이게 정보 꼬임의 원인.

### 출고 현황의 읽기 방식 (확정)
- ✅ **Firestore 직접 읽기**: `const orders = await window._FS.get('orders');` 만 사용
- ❌ `getOrders()` / `DB.get('orders')` / `window._mem` 사용 **금지** (로컬 폴백 섞임)
- ❌ `localStorage` / `sessionStorage` 직접 접근 **금지**
- ❌ shipping.js 자체 캐시·로컬 저장 **금지**

### 서버 미수신·실패 시 동작 (확정)
- `window._FS` 없음 → 렌더 중단 + 안내: "서버에 연결할 수 없습니다 · 새로고침"
- `_FS.get('orders')`가 throw 하거나 `null` 반환 → 렌더 중단 + 같은 안내. **로컬로 채우지 않음. 빈/이전 데이터로도 채우지 않음.**
- 즉 **서버에서 받은 값이 있을 때만 화면을 그린다.** 못 받으면 차라리 빈 화면 + 새로고침 안내.

### 쓰기(출고완료)도 서버 직접 (2026-06-01 갱신 — 코덱스 리뷰 High-1 반영)
- `changeOrderStatus()`는 `DB.get('orders')`(=`_mem` 로컬 미러)를 읽고 `DB.set()`으로 서버에 통째로 덮어쓴다. 서버 미수신으로 `_loadLocalFallback`이 돌았던 PC에선 **로컬 데이터로 서버를 오염**시킬 수 있어 **사용 금지**.
- 출고완료는 `_serverCompleteShip(orderId)`로 처리 (코덱스 2차 리뷰 반영):
  ① `_FS.get('orders')` 서버 최신 → ② 해당 발주서만 출고완료로 갱신(**단일 쓰기**; 발주확정은 출고준비 이력 동반) →
  ③ `_FS.set('orders', …)` 서버 기록 → ④ `_FS.get` **재조회로 실제 반영 검증** → ⑤ 검증 성공 시에만 `_mem` 동기화 + 성공 토스트.
- **왜 검증(④)이 필수**: `_FS.set`은 실패해도 throw하지 않고 삼킨다(index.html). 검증 없이는 서버 저장 실패를 "성공"으로 오판하고 `_mem`까지 오염될 수 있음(코덱스 High-1).
- 발주확정→출고완료를 **단일 get-set 1회**로 처리 → 경쟁 창 2개→1개로 축소, 중간상태(출고준비) 잔류 제거. 실제 거친 단계는 statusHistory에 보존.
- 근거: 출고준비/출고완료 전환은 재고차감·이카운트 부수효과 없음(상태+이력만).
- **알려진 한계(앱 공통)**: orders 전체 배열을 통째로 read-modify-write → get-set 사이 타 기기 동시수정분 유실 가능. 근본 해결은 Firestore 트랜잭션/문서 분리(별도 과제). 이 화면은 경쟁 창을 행위당 1회로 최소화.
- 상태 뱃지는 앱 표준 `orderStatusBadge()` 재사용(발주서 목록/상세와 동일 표기).
